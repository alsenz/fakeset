import { Aside, FileTree } from '@astrojs/starlight/components';

The **insurance** example ships in `examples/insurance/` and shows four features that
work together in realistic schemas: **object fields** (nested structs), **variant
types** for categorical columns, **list links** for embedding policy details inside
contracts, and **expression fields** for derived columns.

## Running the example

```bash
cargo run --bin fakeset -- examples/insurance --output ./output/insurance
```

Output is written to `./output/insurance/`:

<FileTree>
- output/insurance/
  - customers.parquet
  - policies.parquet
  - contracts.parquet
  - claims.parquet
  - premiums.parquet
</FileTree>

## Dataset structure

```
customers (500 rows)
  └── contracts — 60% of customers; links policies → covered_policies list
        ├── claims    — 40% of contracts; derived net_payout expression
        └── premiums  — 85% of contracts; billing records

policies (20 rows)   — referenced by contracts via list link
```

## Key patterns

### Object fields

`customers` uses `type: object` to embed a structured address directly in the row.
The sub-fields are generated independently and stored as a nested struct column in
the Parquet output.

```yaml title="customers.yaml"
- name: address
  type: object
  fields:
    - name: street
      type: string
      generator: street_name
    - name: city
      type: string
      generator: city_name
    - name: zip_code
      type: string
      generator: zip_code
    - name: country
      type: string
      generator: country_name
```

### Variant types

Categorical columns with a known set of values and optional frequency weights use
`type: variant`. The final variant in the list receives whatever probability remains
after the declared ratios are summed, so you don't need to specify it explicitly.

```yaml title="contracts.yaml"
- name: status
  type: variant
  variants:
    - value: "active"
      ratio: 0.7
    - value: "lapsed"
      ratio: 0.2
    - value: "cancelled"    # receives the remaining 10%
```

`policies` uses the same mechanism for `policy_type`, giving the five product types
(home, auto, life, health, travel) equal or near-equal weighting.

### List links

`contracts` links to `policies` so that each contract row embeds 1–3 policy objects
drawn from the product catalogue. Fields in the `content:` block pull values directly
from the drawn policy row:

```yaml title="contracts.yaml"
links:
  - file: policies.yaml
    ref: policy
    cardinality:
      min: 1
      max: 3
data:
  - name: covered_policies
    type: list
    content:
      from: policy
      fields:
        - name: policy_id
          ref: policy.policy_id
        - name: policy_type
          ref: policy.policy_type
        - name: coverage_limit
          ref: policy.coverage_limit
```

### Expression fields

`claims` derives `net_payout` from two other columns in the same row using a SQL
expression. Expressions are evaluated after all other columns are generated, so they
can reference any non-expression field in the dataset.

```yaml title="claims.yaml"
- name: claim_amount
  type: number
  precision: 2
  range:
    min: 100.00
    max: 500000.00
- name: deductible
  type: number
  precision: 2
  range:
    min: 0.00
    max: 5000.00
- name: net_payout
  expression: "claim_amount - deductible"
```

<Aside type="note">
Expressions must appear **after** the fields they reference in the `data:` list.
fakeset evaluates them in declaration order via a DataFusion CTE chain.
</Aside>

### Include chains and field inheritance

`claims` and `premiums` both include `contracts`, which itself includes `customers`.
Ref fields thread IDs down the chain so that, for example, a claim row can carry the
originating customer's ID without the schema explicitly re-declaring the customer
lookup:

```yaml title="claims.yaml"
include:
  file: contracts.yaml
  ref: contract
  ratio: 0.4
data:
  - name: contract_id
    ref: contract.contract_id   # inherited from contracts
  - name: customer_id
    ref: contract.customer_id   # contracts already inherited this from customers
```

The customer ID passes through two include levels (`customers → contracts → claims`)
with no extra plumbing in the intermediate schema.
