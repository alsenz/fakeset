# MULT-3: Include convenience helpers and structural cleanup

Quality-of-life improvements: field wildcard copying, single-field projection from linked lists, and a structural rethink of how pool relationships and nested lists are expressed — collapsing three distinct include types (`Include`, `ContentInclude`, `Couple`) down to one and significantly reducing indentation depth.

_Note_: The fundamental architectural tenet that children by inclusion are generated first, and data subsequently accumulates towards parents in segments, never changes.

---

## Structural redesign (S1 + S2)

These two changes form the core of MULT-3. They are implemented first because Features 1 and 2 are built on top of the cleaned-up model.

### S1. `couple` → dataset-level `links`

**Current model (MULT-1/2):**
```yaml
include:
  file: individuals.yaml
  ref: individuals
  ratio: 0.1
  cardinality: {min: 1, max: 6}
  couple:                        # ← nested inside include, one level deep
    file: organisations.yaml
    ref: organisations
    ratio: 1.0
```

**New model:**
```yaml
include:
  file: individuals.yaml
  ref: individuals
  ratio: 0.1
  cardinality: {min: 1, max: 6}
links:                           # ← dataset-level sibling of include, a list
  - file: organisations.yaml
    ref: organisations
    ratio: 1.0
```

`links` is a `Vec<Include>` on `SyntheticDataset` — it reuses the same `Include` struct as the driver `include`. This eliminates the `Couple` struct entirely and removes one level of indentation.

**Semantics:** for each row generated by the driver (`include`), one row is sampled from each link. Multiple links = multiple pool partners per junction row — the original `couple` behaviour extended to a chain. Each link entry uses the same fields as `Include` (`file`, `ref`, `ratio`, `cardinality`, `reinforcement`) with context-specific validation.

**Pool indices:** with multiple links, each requires its own pool-index sentinel (`_pool_idx_0`, `_pool_idx_1`, …). The planner allocates one sentinel column per link and wires collect bindings to the appropriate index.

**Model changes:**
- `SyntheticDataset`: add `links: Vec<Include>` (default empty)
- `Include`: remove `couple: Option<Couple>`
- `Couple` struct: **deleted**
- MULT-2 test fixtures using `couple:` → update to `links:`

### S2. `content.include` → dataset-level `links` + `content.group`

**Current model (MULT-1/2):**
```yaml
name: wards
rows: 8
data:
  - name: on_call_doctors
    type: list
    content:
      include:                   # ← 3 levels deep by the time you reach fields
        file: doctors.yaml
        ref: doctors
        cardinality: {min: 2, max: 5}
        ratio: 0.33
      fields:
        - name: doctor
          type: string
          ref: doctors.full_name
```

**New model:**
```yaml
name: wards
rows: 8
links:
  - file: doctors.yaml
    ref: doctors
    cardinality: {min: 2, max: 5}
    ratio: 0.33
data:
  - name: on_call_doctors
    type: list
    content:
      group: doctors             # ← references the link by its ref name
      fields:
        - name: doctor
          type: string
          ref: doctors.full_name
```

`group: <ref>` on `content:` declares which link's rows are grouped (by outer slot) to form the items of this list. The include spec (file, ref, cardinality, ratio, reinforcement) moves entirely to dataset-level `links:`, giving cleaner separation of "which dataset" from "what fields each item has".

A link with a corresponding `group` in a list field is a **list link**. A link with no `group` reference is a **junction link** (contributes a sampled row per junction row without producing a list column — the directorships use case). Both use the same `Include` struct; the distinction is purely in how the planner uses them.

**Multiple list links:** a dataset can have multiple links each referenced by a different list field's `group:`.

**Validation:**
- `group: <ref>` must resolve to a link in the dataset's `links` list.
- A link may be referenced by at most one `group:` field (otherwise assembly is ambiguous).
- Existing validation for nested-include content (field types, ref targets, collect bindings) is unchanged.

**Model changes:**
- `ListContent`: remove `include: Option<ContentInclude>`; add `group: Option<String>`
- `ContentInclude` struct: **deleted**
- MULT-2 test fixtures using `content.include:` → update to `links:` + `content.group:`

### S3. `Include` is now the single universal include type

After S1 and S2, `Couple` and `ContentInclude` are gone. `Include` covers all three former roles:
- Driver: `dataset.include` (as before)
- Junction link / list link: entries in `dataset.links`

The only differences between uses are validation rules (e.g. `cardinality` meaning differs depending on whether this is a driver or a link). This is now a pure internal refactor: validation dispatches on context, not type. No YAML-format changes.

## Features

Features are implemented after S1/S2 so they operate on the unified model.

### 1. `include.fields` / `links[].fields` — field wildcard copy

A string list of fields (supporting `*` wildcards) automatically copied into the child dataset's `data` (for driver `include`) or into a list field's `content.fields` (for list links). Eliminates repetitive field declarations.

```yaml
include:
  file: people.yaml
  ref: person
  fields: ["*"]          # copy all fields from people.yaml
  exclude: [internal_id] # optional: suppress specific fields
```

`exclude` is only valid alongside `fields`.

Applies to `include` (driver) and all entries in `links`.
For a list link, `links[i].fields` copies fields into the associated list field's `content.fields`.

**Implementation notes:**
- Model: add `fields: Option<Vec<String>>` and `exclude: Option<Vec<String>>` to `Include`.
- Expansion happens during the `resolve_refs` rewrite phase, after all schemas are loaded. Wildcards are expanded against the include target's resolved schema.
- `*` matches all top-level field names. Nested-path wildcards are not supported.
- Exclusions apply after expansion. A non-existent field name in `exclude` is a validation warning. A wildcard producing zero fields after exclusions is also a warning.
- Validation: `exclude` without `fields` → error.

### 2. `content.group` + `project` — single-field projection

Only valid when `content.group` is present. `project` names one field from the linked dataset to project, making the nested list a simple scalar list rather than a list of structs.

```yaml
links:
  - file: doctors.yaml
    ref: doctors
    cardinality: {min: 2, max: 5}
data:
  - name: on_call_doctors
    type: list
    content:
      group: doctors
      project: doctors.full_name   # → list of strings, not list of structs
```

Output: `on_call_doctors: ["Dr Alice", "Dr Bob", ...]`

The `linkref.fieldname` form distinguishes the projected field from outer-scoped fields and is forward-compatible if `group:` ever becomes a list (multiple groupings per list field — more complex junction table, not planned now).

When `project` is used, `content.fields` must be absent — combining them is a validation error.

**Implementation notes:**
- Model: add `project: Option<String>` to `ListContent`. Value is parsed as `"<ref>.<field>"` — the same `split_ref` convention used elsewhere.
- Validation: error if both `project` and `content.fields` are non-empty. Error if the ref part of `project` does not match any entry in `links`. Error if the field part does not exist in that link's target schema.
- Execution: `execute_assemble_nested_include` detects `project` on the list spec. Instead of building a `StructArray` → `ListArray`, extract the named column from the inner flat and assemble a scalar `ListArray` directly. Arrow element type comes from that column's type.
- The `execute_inner_flat` pipeline is unchanged; only assembly differs.

### 3. `fields[].hidden` — suppress field from output

**Already implemented in MULT-1** (`Field.hidden: bool`, `filter_hidden_columns`). No new model or execution work.

MULT-3's task is test coverage:
- `hidden: true` on a plain field is excluded from CSV/Parquet/JSON output.
- `hidden: true` on a `refs` collect-binding field (MULT-2 use case) is excluded from output while the binding still fires.
- `hidden: true` does not affect validation, ref resolution, or expression evaluation.

## Remaining naming / cleanup

### S4. Internal naming: `rich_list` / `rich_include` → `nested_include`

"Rich list" and "rich include" are internal terms in function names and test fixture directories. MULT-3 completes the rename:
- Rename any remaining `rich_list`, `rich_include`, `rich_content` identifiers in source code.
- Rename test fixture directories: `tests/fixtures/execute/rich_list/` → `nested_include/`, etc.
- Pure rename; no logic changes.

### S5. Naming consistency: `distribution` → `ratio` on variant type fields

MULT-1 renamed `include.distribution` → `ratio`. Two `distribution` fields remain in the model:
- `FieldVariant.distribution: Option<f64>` — weight of one variant choice
- `VariantSchema.distribution: Option<f64>` — row-fraction for one dataset variant

Rename both to `ratio` with `#[serde(alias = "distribution")]` for backward compat. Update callers in `expand_variants.rs`, `validate.rs`, `plan.rs`, and any fixture YAML that uses `distribution:` on variant fields.

## High-level implementation plan

**Prerequisites:** MULT-2 complete.

### Stage 1 — Structural redesign (S1, S2, S3) ✓ DONE

The biggest change. Remove `Couple` and `ContentInclude`; add `SyntheticDataset.links`; replace `content.include` with `content.group`. Update model, graph, validate, rewrite, plan, executor across all modules. Update MULT-1 and MULT-2 test fixtures. `cargo check` + full test suite must pass at zero failures. At the end of this stage, `Include` is the only include type.

This stage is deliberately first so all subsequent work targets the clean model.

### Stage 2 — Naming consistency (S4, S5) ✓ DONE

Internal renames and `distribution` → `ratio` on variants. No user-facing YAML changes; serde aliases preserve compat. Pure refactor: `cargo check` + `cargo test` at zero failures.

### Stage 3 — `include.fields` wildcard expansion (Feature 1) ✓ DONE

Add `fields`/`exclude` to `Include`, expand wildcards in the rewrite phase, validation rules, test fixtures.

### Stage 4 — `project` single-field projection (Feature 2) ✓ DONE

Add `project` to `ListContent`, validation, assembly-path change in `execute_assemble_nested_include`, test fixture.
Also fixed pre-existing bug: `_pool_idx` leaked into nested list struct items (now stripped before assembly).
Also implemented hidden-field filtering for nested content item fields (required for Stage 5 collect-binding case).

### Stage 5 — `hidden:` test coverage (Feature 3) ✓ DONE

Explicit test coverage for the already-implemented `hidden:` flag across plain fields, collect-binding fields, and expression fields.
